Overview

Objects, not pools

AIOS is a small C++20 cluster object store: durable objects on local filesystems, gossip membership, and consistent-hash placement. Layout and storage class are chosen per object version at write time. There are no pools or placement groups.

Cluster

Gossip + map

aiosd peers join over signed TCP++ gossip. Each node rebuilds the same cluster map (epoch, targets, classes) from advertised capacity.

Place

Class-scoped ring

place(oid, class, n) walks a vnode ring. Primary is first in the acting set. Membership change remaps about 1/N of objects.

Durability

Replica or EC

Replica fan-out, or erasure coding (k+m, XOR or ISA-L). Optional class transitions, cold bags, and POSIX/VBD backup.

Experimental. Do not use it in production or with anything other than test data.

Architecture

Primary coordinates; HTTP 307 to find it

Clients talk to the primary for an object. Wrong node returns 307 with Location. The primary replicates or erasure-codes across the acting set.

Storage targets are mounts with a top-level .aios marker (storage_class required). Empty peer list = bootstrap node.

Frontends

One POSIX volume, several doors

libaios_posix is a hierarchical filesystem on objects (inode 1 = /, striped files, changelog dirs). S3 and XRootD sit on that ABI. A kernel virtual block device, aiosvd, exposes object-striped volumes as /dev/aiosvdN.

FUSE, kernel aiosfs, S3, and XRootD share the POSIX volume. aiosvd is a separate object-striped block device (COW clones, discard; optional NFS of aiosfs). Raw object clients PUT/GET oids directly.

XRootD

Stock XrdOfs, AIOS as the OSS

The gateway is an ordinary xrootd process. libXrdAios.so is an OSS plugin: filesystem ops become aios_posix_* calls against a mounted volume. Clients stay xrdcp / ROOT / XrdCl.

Build when CMake finds XRootD ≥ 5 (AIOS_WITH_XROOTD, XRootD_ROOT). If XRootD is absent, the plugin is skipped. Features bit: XRDOSS_HASNAIO.

XRootD

Identity is a local passwd map

Each client op reads XrdSecEntity::name, maps it with getpwnam_r, and sets the POSIX caller. Mode bits on AIOS inodes then apply. Unknown names fail closed.

Caller

entity.name → uid/gid

  • Missing or unknown name → -EACCES
  • Mapped uid 0 → POSIX root bypass
  • No env (internal server call) → mount defaults
  • Opener uid/gid stored on the file; restored on Read/Write/Close
  • Configure sec.protocol so name is a local account
I/O

ReadV is one prefetch

  • ReadV calls aios_posix_prefetchv first
  • Covering stripe chunks, then each iovec via Read
  • Same 256-range / 256 MiB cap as FUSE/kernel AIOS_IOC_PREFETCHV
  • Create, open, write, stat, mkdir, rmdir, unlink, rename, truncate, chmod, readdir
  • No TPC, AIO, or proxy FSctl in v1

FUSE, S3 IAM, and XRootD all go through aios_posix_set_caller. Quotas and QoS on the POSIX volume therefore apply to XRootD writes as well.

Bring-up

aiosd, then a closed OSS config

Cluster

./build/aiosd --cluster-key "$KEY" \

  --node-id a --listen 0.0.0.0:7400 \

  --http-listen 0.0.0.0:7480

At least one mount with a .aios marker, or puts fail with no_targets.

xrootd.cf

all.export /

ofs.osslib libXrdAios.so

aios.endpoint 127.0.0.1:7480

aios.cluster_key $KEY

aios.volume default

sec.protocol unix

Parms after the library path also work: ofs.osslib libXrdAios.so endpoint=… cluster_key=…. Env fallbacks: AIOS_ENDPOINT, AIOS_CLUSTER_KEY. The client login name must exist in the server passwd DB.

Status

Early, and deliberately small

Done

  • POSIX ABI, FUSE, aiosfs, VBD /dev/aiosvdN
  • libXrdAios OSS + ReadV prefetch
  • Archive bags, backup, quota, QoS
Not this plugin
  • TPC, AIO, proxy FSctl
  • An XRootD-native object API
  • A replacement for EOS or XCache
  • Production auth beyond passwd + HMAC
  • Kernel TLS (HTTP path stays private-net)
Next
  • Keep XRootD as a POSIX door, not the core
  • Harden identity (opener vs later ops)
  • Same volume as FUSE/S3 in tests
  • Docs: proto/xrd_oss.md
